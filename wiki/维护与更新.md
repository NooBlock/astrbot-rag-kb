# 维护与更新

本页讲长期运营：新增/修改语料后怎么重建、换 embedding 模型会发生什么、怎么备份迁移，以及给「动态更新层」搭一条定时流水线。

前置约定：

- 只修改仓库 `corpora/` 下的语料文件；`tools/` 是通用工具，不需要改。
- 命令均在仓库根目录执行；`<ASTRBOT_DATA>` 指 AstrBot 的 `data/` 目录（内含 `cmd_config.json`）。
- `python` 指 AstrBot 所在环境的 Python 3.12。

## 新增一个语料库

AstrBot 知识库按 `manifest.json` 的 `kb_name` 识别，工具按目录名前两位数字扫描，所以新增库要遵守命名：

```text
corpora/06_dynamic/          # 目录名必须是「两位数字_英文短名」
├─ chunks.jsonl              # 每行 {"id": int, "text": str}
├─ manifest.json             # 至少含 kb_name/description/emoji/source_url/num_chunks
└─ README.md                 # 来源、许可、构建方法、已知局限
```

步骤：

```bash
# 1) 准备语料（格式见 docs/数据字典.md），保证 text 自包含、无重复、UTF-8 无 BOM
# 2) 校验
python tools/validate_corpus.py corpora/06_dynamic

# 3) 建库并导入（--only 只处理这一个库）
python tools/build_kbs.py --config <ASTRBOT_DATA>/cmd_config.json --only 06_dynamic

# 4) 验证
python tools/verify_kbs.py --config <ASTRBOT_DATA>/cmd_config.json
```

字段怎么填、`num_chunks` 怎么对齐，见 [docs/数据字典.md](../docs/数据字典.md)。建议同时更新 `SPEC.md` 中的库清单，并在 `manifest.json` 的 `notes` 里写清构建方式与局限。

## 修改已有语料

```bash
# 1) 编辑 chunks.jsonl / manifest.json（改完把 manifest 的 num_chunks 改成实际条数）
# 2) 校验（会检查条数一致、重复、超长）
python tools/validate_corpus.py corpora/01_cheer_terms

# 3) 重建（脚本按 sha256 判断，内容变了才会重建；没变会跳过）
python tools/build_kbs.py --config <ASTRBOT_DATA>/cmd_config.json --only 01_cheer_terms
```

重建判断逻辑（`corpora/_state/imported.json` 记录 `num_chunks` + `sha256`）：

| 情况 | 结果 |
| --- | --- |
| 文件没变（哈希一致） | 跳过导入，几秒完成；仍会同步 `manifest.description` 的变更 |
| 文件变了（哈希不一致） | 删除旧库 → 按 `manifest` 重建 → 全量导入 |
| 没有状态记录（新库） | 直接建库并导入 |
| 加 `--force` | 无视记录，删库重建 |

注意事项：

- **只改 `emoji` 不会自动同步**（脚本只在 `description` 变化时更新元信息），需要删库重建或在 WebUI 里手动改。
- **改 `kb_name` 等于新建库**：旧库还留在 AstrBot 里，需要到 WebUI 或调用删除接口清理，否则会出现两个近似知识库。
- 只改各库的 `README.md` 不影响导入，但它是来源与局限的正式记录，建议与数据同步更新。
- 修改后请更新 `manifest.json` 的 `built_at`、`notes`，便于追溯。

## 增量与全量
<a id="增量与全量"></a>

**结论：当前设计下，改任何一条 chunk 都会整库重建。** 原因是预切块导入以「文档」为单位：

- 只删除/替换部分文档，AstrBot 的 `doc.db` 里可能留下孤儿 chunk，`chunk_count` 与预期对不上；
- 脚本宁可整库删除重建，也不做不安全的局部更新。

因此：

| 操作 | 实际成本 |
| --- | --- |
| 改 1 条 | 整库重新 embedding（例如 1804 条的库要重算 1804 条） |
| 加 10 条 | 同上 |
| 新增一个独立库 | 只算新库的 embedding |

如果确实要「只追加、不重建」：可以用 API 再导入一个新文档保留旧文档，但 `_state/imported.json` 会与线上状态不一致，下次 `build_kbs.py` 会判定「哈希变化」把整库重建。**不建议**在脚本体系内混用这种手工增量。

多库维护时用 `--only` 限定范围，避免一次改动牵连 5 个库：

```bash
python tools/build_kbs.py --config <ASTRBOT_DATA>/cmd_config.json --only 01_cheer_terms,03_ruozhiba
```

## 更换 embedding 模型的后果

<a id="更换-embedding-模型的后果"></a>

知识库在创建时绑定 embedding 模型和维度，**创建后不可修改**；索引里存的是该模型生成的向量。

- **换模型 = 换向量空间**：旧索引与新模型不兼容，轻则召回质量崩坏，重则直接报维度/相似度错误。
- **同一维度也不行**：两个模型即使都输出 1024 维，向量语义空间也不同，不能混用。
- **修改提供商配置同样危险**：不要直接改某个已被知识库使用的 provider 的模型名或维度，会破坏现有索引（AstrBot 文档明确提示）。

正确做法：

1. 在 WebUI 新增一个 embedding 提供商（新模型、新维度），不要覆盖旧的；
2. 删除旧知识库（或改名保留作对照）；
3. 用新 provider 重新建库 + 全量导入；
4. 更新文档与配置里的模型/维度记录。

```bash
# 示例：新模型就绪后，重建全部 5 个库
python tools/build_kbs.py --config <ASTRBOT_DATA>/cmd_config.json --force
```

参考成本：本项目快照（4544 条、约 115 万字符）在 SiliconFlow `Qwen/Qwen3-Embedding-8B` 上全量导入耗时约 3–4 分钟（各库 6–78 秒），实际取决于服务商速率与限流。

同一 AstrBot 里不同知识库用不同 embedding 模型在接口层面是允许的（每个库独立记录），但**跨库检索的一致性、维护复杂度都会变差**；除非有明确理由，建议所有库统一模型。

## 备份与迁移

<a id="备份与迁移"></a>

### 方式一：WebUI 备份（推荐）

WebUI → **设置 → 备份管理 → 导出备份**：生成的 ZIP 包含主数据库、知识库（元数据 + 向量索引 + 文档）、配置文件、附件与技能。恢复用 **导入备份**，注意它会**清空并覆盖现有全部数据**，且恢复后建议重启 AstrBot。

适合：同版本、同 embedding 模型的迁移或日常备份。

### 方式二：手工复制数据目录

1. 停止 AstrBot（避免 SQLite / faiss 文件写入中断）；
2. 复制 `astrbot/data/knowledge_base/`（`kb.db` + 每个 `<kb_id>/` 下的 `doc.db`、`index.faiss`、`files/`）；
3. 复制 `astrbot/data/cmd_config.json`（或对应配置文件）里的知识库与 provider 配置；
4. 目标机启动 AstrBot，确认 provider（模型名、维度、API 地址）与来源一致。

不合法的做法：**不要**只复制某个 `doc.db` 或 `index.faiss` 到另一个库 ID 下，也不要在换模型后复用旧索引。

### 方式三：只搬语料，重新导入（最稳、最可移植）

把 `corpora/` + `tools/` 带到新机器，在新环境重新跑 `build_kbs.py`。代价是要重新消耗 embedding，但完全不受旧版本、旧路径、旧库 ID 影响。**跨 embedding 模型迁移只能走这条路。**

备份建议：语料与 `manifest.json` 进 git；知识库索引体积大且可重建，不必进 git。

## 动态更新层：定时补充新梗
<a id="动态更新层定时补充新梗"></a>

静态快照会过时。建议单开一个 `06_dynamic`（或按主题拆）作为动态层，**不要直接改 01 释义库**——释义库有许可与质量问题，混入自动抓取内容会破坏其可解释性。

推荐流水线（每周一次足够）：

```text
① 盘点/搜索：抓取公开热词页/榜单 API（保留抓取时间与 URL）
② 结构化：每个词条 → 【词条】【释义】【出处/时间】【用法/例句】
③ 过滤去重：与现有 01~05 及本批内容做文本/近义去重；过滤广告、敏感、无法核实的内容
④ 分桶合并：按主题把 4–6 条合并为一条自包含 chunk（避免整篇长文）
⑤ 校验：python tools/validate_corpus.py corpora/06_dynamic
⑥ 入库：python tools/build_kbs.py --config <ASTRBOT_DATA>/cmd_config.json --only 06_dynamic
⑦ 冒烟：python tools/verify_kbs.py --config <ASTRBOT_DATA>/cmd_config.json --query "<本批新梗>"
⑧ 抽检：每批随机抽 20 条人工复核，记录在 manifest.notes
```

工程建议：

- 每期产物保留来源 URL、抓取时间、抓取脚本版本；`manifest.built_at` 与 `notes` 随批次更新。
- 用固定随机种子抽样（参考 03 的 `seed=20261026`），保证可复现。
- 抓取加间隔、遵守 robots 与平台条款；失败重试 + 指数退避；数据源限流时降低频率而不是加大并发。
- 定时任务可以是系统计划任务 / cron / CI（GitHub Actions），只要机器能访问 AstrBot 与 embedding 服务；**不要把 `cmd_config.json` 或 token 写进 CI 配置**，用 CI Secret 或干脆在本地机器跑。
- 若使用 GitHub Actions 自动更新，建议只跑「抓取 → 生成语料 → 校验 → 建 PR」，「入库」留给人工确认，避免自动内容直接进生产。

## 成本与限流

| 环节 | 成本来源 | 优化 |
| --- | --- | --- |
| 首次全量导入 | 4544 条 × 平均约 250 字符 ≈ 115 万字符的 embedding 调用 | 只建需要的库；先用 `--only` 试一个库 |
| 重建 | 每次改语料都要重算整库 | 集中修改、减少重建次数；用 `--only` 限定范围 |
| 查询 | 每条消息的 query embedding + 检索结果 token | 默认 `kb_fusion_top_k=20`、`kb_final_top_k=5` 已较保守，不要盲目调大 |
| 对话模型 | 注入的片段会占用上下文 | Agentic 模式按需检索；或减少挂载的库数量 |
| 本地 embedding | CPU/GPU 占用 | 批量建库时避免同时跑其他重任务 |

限流处理：降低 `batch_size` / `tasks_limit`（脚本默认 32 / 3），或提高 `max_retries`；服务商返回 429 时等待后重试，不要把并发调高。导入任务本身是后台任务，脚本会轮询直到 `completed` 或超时。

## 变更记录建议

- 语料变更随 git 提交，提交信息写清「哪个库、增删改多少条、来源」；
- `manifest.json` 的 `built_at` / `notes` / `num_chunks` 与数据保持一致；
- `corpora/_state/imported.json` 由脚本自动维护，**不建议手改**。新机器/新实例上它不存在也能正常工作；但**不要在库已有数据时删除它**——脚本会把它当作「未导入」而重复导入，导致 `chunk_count` 校验失败（真发生了就用 `--force` 删库重建）。
